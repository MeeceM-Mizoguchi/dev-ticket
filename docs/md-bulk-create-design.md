# MDファイルからチケット一括作成 設計書

> 対象: 「一括作成」ボタンにメニューを追加し、**MDファイルを取り込んでチケットを一括生成**する。
> AI（Claude 等）にMDを書かせる運用を前提とし、**テンプレート／プロンプトのワンボタンコピー**も同梱する。
> ステータス: **実装済み**（`npx vite build` 緑。実ファイル6件＋テンプレートで解析を検証済み）

## 2. アーキテクチャ

Markdown の解析基盤は **既存の `src/app/lib/markdown/` をそのまま流用**する（`docs/paste-markdown-format-design.md` で作った IR）。新規に書くのは「IR → チケット」の写像だけ。

```
 .md File（複数可）
    │  file.text()
    ▼
 mdTextToTickets(text, ctx)             ← 新規（行単位で走査。理由は §3-1-1）
    │   ・見出しレベルで親子にグルーピング
    │   ・見出し直後の箇条書きから「キー: 値」のメタを抽出
    │   ・残りの行だけを parseMarkdown() → mdBlocksToHtml() で詳細HTMLへ（既存）
    ▼
 ParsedTicket[] + ParseWarning[]        ← 確認画面の描画元
    │  「チケット化する」
    ▼
 insertBulkTickets(...)                 ← 新規（既存 handleSave からの共通化）
    │   ・WBS採番（親 T-001 / 子 T-001-1）
    │   ・sprint_tickets 一括 insert
    │   ・notifications insert / emitLinkItemsChanged
    ▼
 createdWbs: string[] → SprintPage      ← スクロール＋ハイライト
```

## 3. MDフォーマット仕様

### 3-1. 構造

```md
## ログイン画面のバリデーション追加          ← 親チケットのタイトル
- ステータス: 未着手                        ← ここからメタ（先頭の連続する1リストのみ）
- 優先度: 高
- 担当者: 山田太郎
- 開始日: 2026/08/03
- 期限日: 2026/08/10
- 見積工数: 4

メールアドレス形式のチェックを追加する。      ← 残りのブロックはすべて「詳細」
対応範囲:
- 半角英数のみ許可
- 全角は弾く

### 入力フォームのUI修正                     ← 1段下の見出し ＝ 子チケット
- 優先度: 中
- 見積工数: 2

プレースホルダを調整する。

## ログ出力の整備                            ← 次の親チケット
- 見積工数: 8
```

3つのルールだけで成立する:

1. **見出し = タイトル**。ファイル内で**最も浅い見出しレベル**を親、その**1段下**を子とする。2段以上下の見出しは詳細本文に含める。コードブロック（``` ```` ```）の中の `#` は見出しとみなさない。
2. **見出し直後に続く箇条書きのひとかたまり**から、`キー: 値` 形式かつ**既知キー**の行を**メタ情報**として取り出す。かたまりは空行または非箇条書き行で終わる。既知キーでない項目（`- 備考: …` や普通の箇条書き）は捨てずに詳細へ戻す。既知キーが1つも無ければ、かたまりごと詳細として扱う。
3. **メタ以外はすべて詳細**（`mdBlocksToHtml()` でHTML化して `description` に入る。表・コード・引用・入れ子リストもそのまま保持される）。

### 3-1-1. メタ抽出を「行単位」で行う理由（重要）

`parseMarkdown()` でブロックへ変換してからメタを探す実装は**破綻する**。実際のAI出力はメタ行と本文の間に空行を入れないことが多く、その場合 Markdown の**遅延継続行（lazy continuation）**として本文が最後のメタ項目に吸収され、**詳細が丸ごと消える**。さらに本文の後ろにある箇条書きまで同じリストへ融合し、「キー: 値」でない項目が混ざるせいで**メタ全体が詳細へ落ちる**。

```md
## 検索APIのレスポンス改善
- ステータス: 進行中
- 見積工数: 8
N+1クエリを解消し、一覧取得のレスポンスタイムを短縮する。   ← 空行が無い
対象は以下の通り。

- 商品一覧エンドポイント                                     ← 上のリストへ融合する
```

したがって `mdTextToTickets()` は **生テキストを行単位で走査**し、見出しでセクションに切る → 先頭の箇条書きのかたまりからメタを抜く → **残りだけを** `parseMarkdown()` に渡す、という順序にしている。これで空行の有無に関わらず正しく分かれる。

**文書タイトルの扱い**: 最も浅いレベルの見出しが1つしかなく、**メタ行を1つも持たず、かつ1段下の見出しが存在する**場合、それは文書タイトルとみなして無視し、1段下を親レベルに繰り上げる（`# スプリント計画` → `## チケット…` の形が自然に通る）。3条件すべてを満たす場合に限る（「メタなしのチケットが1件だけ書かれたファイル」を誤って空にしないため）。

**見出しが1つも無いファイル**: チケット0件として扱い、確認画面に「チケットが見つかりませんでした」を表示する。

### 3-2. メタのキー

キーは**全角/半角コロン・大文字小文字・前後空白を無視**して照合する。太字（`**優先度**: 高`）も剥がして照合する。

| キー | 別名 | 値 | 未記載時 |
|---|---|---|---|
| ステータス | status, 状態 | 未着手 / 進行中 / レビュー中 / レビュー完了 / STG完了 / UAT完了 / クローズ | **未着手** |
| 優先度 | priority | 高 / 中 / 低 | **中** |
| 分類 | カテゴリ, 種別, category | プロジェクトに登録済みの分類名（`ticket_categories`） | 空白 |
| 担当者 | assignee, 担当 | プロジェクトメンバー名 | 空白 |
| 開始日 | start, 開始 | `2026/08/03` `2026-8-3` | 空白 |
| 期限日 | due, 期限, 締切, 終了日 | 同上 | 空白 |
| 見積工数 | estimate, 工数, 見積 | 数値（`4` `4h` `4時間` を許容） | **0** |

未知のキー（例: `- 備考: …`）はメタとして拾わず、詳細本文に残す。

### 3-3. 値の正規化と警告

| ケース | 挙動 | 警告 |
|---|---|---|
| ステータス名が候補外 | 未着手 | 「ステータス『対応中』は候補にないため未着手にしました」 |
| 優先度が候補外（`High` 等） | 英語・全角は正規化して照合。それでも不明なら中 | 同様 |
| 分類がプロジェクトに未登録 | **空白** | 「分類『ばぐ』はこのプロジェクトに登録されていないため分類なしにしました」 |
| 担当者がプロジェクトメンバーに不在 | **空白** | 「担当者『佐藤』はメンバーに見つからないため空欄にしました」 |
| 日付が解釈不能 | 空白 | 「開始日『来週』を日付として読めませんでした」 |
| 期限日 < 開始日 | 値は保持 | 「期限日が開始日より前です」 |
| 見積工数が数値でない | 0 | 「見積工数『大』を数値として読めませんでした」 |
| 見積工数が小数 | 整数へ丸める（DB は int 列） | 「見積工数『4.5時間』を 5 時間に丸めました」 |

警告は**取り込みをブロックしない**（確認画面の黄色ストリップに一覧表示するだけ）。空タイトルの見出しだけはその項目ごとスキップする。

### 3-4. 「未記載は空白」の例外

ご要望は「書かれていなければ空白」だが、`status` / `priority` は型（`TicketStatus` / `Priority`）と DB 制約上「空」を表現できず、既存の表からの一括作成も必須項目としている。したがってこの2つだけは既定値（**未着手 / 中**）を入れる。`estimated_hours` も既存の一括作成と揃えて `0`。担当者・開始日・期限日・詳細は文字通り空白（`null`）で登録する。

### 4-3. MDモーダル ― 画面B（確認）

```
┌─────────────────────────────────────────────────┐
│ MDファイルからチケット作成      Sprint 12    ✕  │
├─────────────────────────────────────────────────┤
│ 📄 sprint12-tickets.md ／ 3件（複数なら「3ファイル」）│
│ 階層  [ 親子で作成 | すべて親チケット ]          │
│ ⚠ 担当者「佐藤」はメンバーに見つからないため…    │
├─────────────────────────────────────────────────┤
│ ☑ 1  ログイン画面のバリデーション追加            │
│        [未着手] [高] [山田太郎] [8/3〜8/10] [4h] │
│ ☑   ↳ 入力フォームのUI修正                      │
│          [中] [2h]                              │
│ ☑ 2  ログ出力の整備                             │
│        [8h]                                     │
│ ☑ 3  リリース手順書の更新                        │
├─────────────────────────────────────────────────┤
│ [別のファイルを選ぶ]        [チケット化する (4件)]│
└─────────────────────────────────────────────────┘
```

**階層トグル**: 同じMDでも「親子で作る／全部フラットに作る」を**取り込み後に切り替えられる**ようにする。MDを書き直させずに使い分けられ、AIが余計に階層を付けてきた場合の逃げ道にもなる。

- `親子で作成`（既定・MDに子見出しがある場合のみ表示）: `### ` を子チケットとして登録
- `すべて親チケット`: 子見出しも独立した親チケットとして登録。表示上のインデント（`↳`）も外れ、通し番号が振り直される
- MDに子見出しが1つも無い場合はトグル自体を出さない

- チェックを外すと登録対象から除外。**親のチェックを外すと子も連動**して外れる（親不在で子は作れないため。`すべて親チケット` 時は連動しない）
- バッジは**値があるものだけ**表示（空欄はバッジ自体を出さない）＝「何が拾えたか」が一目で分かる
- 件数表示・ボタン内件数は**子チケットを含む合計**
- 詳細本文の中身は表示しない（タイトル主体という要件どおり）。行ホバーで先頭100文字を tooltip 表示する程度に留める
- モーダルの高さは既存の一括作成ダイアログと揃えて `90vh` / `min(96vw, 720px)`、リスト部のみスクロール

### 4-4. テンプレート

テンプレートは**1種類だけ**。用途ごとに選ばせる方式（フラット／親子構成／タイトルのみ／バグ報告）は
一度実装したが**廃止した**。判断が要るわりに、どれを選んでも取り込み後に画面側で直せてしまい、
選択自体が意味を持たなかったため。方針は「**全項目を埋めてもらう**」1本に統一する。

```
  AIに書いてもらう場合
  プロンプトをAIに渡し、返ってきたMarkdownを .md ファイルとして保存してから取り込みます。
  ステータス・優先度・分類・担当者・日程・見積工数まで埋めるよう指示が入っています。

  [📋 テンプレートをコピー] [✨ AI用プロンプトをコピー]

  ▾ テンプレートを表示
```

`MD_TICKET_TEMPLATE`（全項目入り・親4件/子2件の記入例）。**1作業で完結するチケットと、親＋子に分けるチケットの両方**を1本に入れてあり、**全チケットの本文が ASIS / TOBE 形式**になっている:

```md
## ログイン画面のバリデーション追加
- ステータス: 未着手
- 優先度: 高
- 分類: バグ
- 担当者: 山田太郎
- 開始日: 2026/08/03
- 期限日: 2026/08/10
- 見積工数: 4

メールアドレス形式のチェックを追加する。
半角英数のみ許可し、全角は弾く。空欄時のエラーメッセージも表示する。

## 検索APIのレスポンス改善
- ステータス: 進行中
- 優先度: 中
- 分類: 仕様確認
- 担当者: 佐藤花子
- 開始日: 2026/08/04
- 期限日: 2026/08/18
- 見積工数: 8

N+1クエリを解消し、一覧取得のレスポンスタイムを短縮する。
対象は以下の通り。

- 商品一覧エンドポイント
- ユーザー一覧エンドポイント
- 注文履歴エンドポイント

## リリース手順書の更新
（以下同様）
```

**親子チケットもこの1本でカバーする**。テンプレートには `## 親` ＋ `### 子` の例が含まれ、
プロンプトにも「親チケットと子チケット」の節がある（§4-5）。取り込み後に階層が不要と分かれば
確認画面の階層トグル（§4-3）でフラットに倒せる。

### 4-5. AI用プロンプト

`src/app/lib/mdTickets/template.ts`

```ts
/** そのまま .md にして書き足せる、全項目入りの記入例 */
export const MD_TICKET_TEMPLATE: string;

export interface MdPromptContext {
  memberNames: string[];
  categoryNames: string[];   // プロジェクトに登録済みの分類名
  sprintName?: string;
  today: string;             // "2026/08/03"
}

export function buildMdTicketPrompt(ctx: MdPromptContext): string;
```

プロンプトに含める内容:

1. 「以下の書式のMarkdownでチケット一覧を出力して。コードブロックで囲まずMDそのものを出す」
2. 親子の使い分け（1作業で完結するものは `##` だけ／複数作業に分かれるものだけ `##` + `###`／`####` 以降は作らない／**子チケットにも同じ項目を書く**／迷ったら `##` だけ）
3. 書式仕様（見出し＝タイトル／`- キー: 値` ＝メタ／空行の後ろ＝詳細）
3-1. **詳細には ASIS（現状）と TOBE（あるべき姿）を必ず両方書く**（子チケットも同様）。太字ラベル＋改行＋本文の形式で、**見出し（`###`）でラベルを書かせない**（子チケットとして解釈されるため）。情報不足で ASIS が書けない場合は推測せず「（要確認）」と明記させる
4. **項目の箇条書きは連続した行でまとめ、終わったら空行を1行入れてから本文を書く**
   （これを守らせないと §3-1-1 の遅延継続行の問題を人手のMDで踏む）
5. 使えるキーと選択肢（ステータス7種・優先度3種・日付は `YYYY/MM/DD`・見積工数は整数）
6. **このプロジェクトのメンバー名一覧と分類名一覧**（担当者・分類に使える値を限定する）
7. 今日の日付とスプリント名
8. 「7項目はできる限りすべて埋める。ただし根拠なく推測しない。判断材料が無い項目は行ごと省略する」
9. 「表に無いキーは使わない（備考・目的などの独自キーも作らない）」
10. 出力例（＝ `MD_TICKET_TEMPLATE`）

### 4-6. コピーの実装

`navigator.clipboard.writeText()` ＋ 既存 `useToast()` で「テンプレートをコピーしました」。クリップボードAPIが使えない環境（非セキュアコンテキスト等）では、失敗時に `<textarea>` を展開して全選択状態にし、手動コピーできるようフォールバックする。

## 5. 登録処理（`insertBulkTickets`）

既存 `BulkTicketCreateDialog.handleSave`（[BulkTicketCreateDialog.tsx:1029-1101](../src/app/components/tickets/BulkTicketCreateDialog.tsx#L1029-L1101)）の DB 部分を切り出し、**表からの一括作成とMDからの一括作成で共用**する。

```ts
export interface BulkInsertTicket {
  title: string;
  status: TicketStatus;          // "todo" 等（DB値）
  priority: Priority;
  assignee: string | null;
  startDate: string | null;      // "2026-08-03"
  dueDate: string | null;
  estimatedHours: number;
  descriptionHtml: string | null;
  children?: BulkInsertTicket[]; // MD経路のみ使用。1階層まで
}

export async function insertBulkTickets(params: {
  sprintId: string; projectId: string; projectSlug?: string;
  createdBy: string | null;
  tickets: BulkInsertTicket[];
}): Promise<{ createdWbs: string[]; error?: string }>;
```

処理順:

1. `sprints` からプロジェクトの `identifier`（プレフィックス）と全 `sprint_id` を取得（既存ロジックそのまま）
2. 親の連番を採番: `${prefix}-${String(n).padStart(3,"0")}`
3. 子の枝番は**親のWBS基準**で `${parentWbs}-${1..}`（既存 `NewTicketDialog` と同形式・ゼロ埋めなし）。**新規作成した親の子なので既存の子は存在せず、1から振れる**
4. 親を insert → 親の `id` を子の `parent_id` に入れて子を insert（`id` はクライアント生成なので**1回の insert にまとめられる**。親子を1配列にして単発 insert する）
5. `notifications` を担当者ありの分だけ insert（既存どおり）
6. `emitLinkItemsChanged(projectId, "ticket")`
7. 作成した WBS を**親→子の表示順**で返す

`progress` は `getDefaultProgressForStatus(status)`、`images: []`、`category_id: null` は既存に合わせる。

### 5-1. プラン上限

`plan.maxTicketsPerSprint` がある場合、**登録直前に「現在の件数＋作成件数」を判定**し、超過するなら登録せずエラー表示（「このプランでは残り N 件までです」）。既存の表からの一括作成は上限判定を持っていないため、この機会に**両方に入れる**（同じヘルパー内で判定するので自動的に揃う）。

## 6. スクロール＋ハイライト

`onCreated(createdWbs: string[])` を親へ返し、`SprintPage` が保持する。

```ts
const [flashWbs, setFlashWbs] = useState<string[]>([]);
// 作成時: setFlashWbs(createdWbs) → 6秒後に []（既存 flashTickets と同じ 6000ms）
```

3ビュー共通で `highlightWbs?: string[]` を props に追加する。

| ビュー | ハイライト | スクロール |
|---|---|---|
| **リスト** | 既存 `isHighlighted` に `highlightWbs.includes(t.wbs)` を OR 追加（背景 `#FFFBEB`）。子チケットも同様 | 対象スプリントを展開＋ハイライト対象の子を持つ親行を展開してから、先頭WBSの `[data-wbs]` へ `scrollIntoView` |
| **ボード** | `TicketCard` に `highlighted` prop。背景 `#FFFBEB` ＋ `box-shadow: 0 0 0 2px rgba(245,158,11,0.45)` | ボードは1スプリント表示なので `setSelectedSprintId(対象)` してから先頭カードへ `scrollIntoView` |
| **ガント** | 左ペインの行と右カレンダー行の**両方**の `background` を `#FFFBEB` に（行の高さが対応しているため片方だけだとズレて見える） | 対象スプリント＋親行を展開してから左ペインの先頭行へ `scrollIntoView` |
| **スプリント詳細** | 既存 `[data-wbs]` 行の背景を差し替え | 既存の `scrollWbsRef` と同じ経路で先頭WBSへ |

実装補助として、各ビューのチケット行／カードに `data-wbs={t.wbs}` を付与する（リストと詳細は既にある。ボードとガントは新規付与）。スクロールは既存の `requestAnimationFrame` → `scrollIntoView({ behavior:'smooth', block:'center' })` の形をそのまま踏襲する。

**再読み込みとの順序**: `refreshSprints()` の完了後に `setFlashWbs()` する。DOMにまだ行が無い状態でスクロールしても無反応になるため、既存リストビューと同じく「対象WBS or 展開状態」を deps にした `useEffect` からスクロールを撃つ（`scrolledForWbs` 相当の ref で二重発火を防ぐ）。

## 7. 既知バグの再発防止チェック

`memory/bug_checklist.md` の該当項目:

- **順番が変わる**: 親→子の順で `createdWbs` を返し、insert も同順。表示順は既存のスプリント再読込に委ねる（独自ソートを持ち込まない）
- **チカチカ**: `highlightWbs` は配列を毎レンダー新規生成せず、`useState` の値をそのまま渡す。ハイライト解除は6秒後の1回だけ
- **子チケットの遅延**: 親子を**1回の insert** にまとめるので、親だけ先に見えて子が後から出る状態は発生しない
