# BRU12-025 ファイルボックス コメント機能 設計書

作成日: 2026-08-17

## 1. 要件

ファイルボックスでビュワーを開いた際、書類の上に直接コメントを残せるようにする。

- エクセル / ワード / PDF などをクリックしてビュワーを開き、
  **「コメント」ボタン、またはキーボードの「c」** でコメントモードに入る
- 基本的にホワイトボードのコメント機能（ENHA2-039）と全く同じ操作感にする
  - カーソルがピンになり、書類をクリックするとその位置に入力欄が出る（Enter は改行 / Ctrl+Enter で保存）
  - 保存するとピンが立ち、投稿内容がそのまま吹き出しで開く（コメントモードは抜ける）
  - ピンにマウスオーバーで吹き出し（投稿者 / 日時 / 本文 / 返信 / 解決 / ⋯メニュー）
  - 「返信を表示（N）」で返信一覧を展開。展開中は固定表示（別の場所のクリック / Esc で閉じる）
  - ⋯メニュー：「リンクをコピー」は全員、「編集」「削除」は投稿者本人のみ
  - 本文の「@メンバー名」でメンション通知＋Slack通知
  - 「解決済み」にするとピンが消え、コメント一覧ポップアップから見返せる
  - ピンはドラッグで動かせる

## 2. 方式

### 2.1 保存先：専用テーブル `project_file_comments`

ホワイトボードはコメントを Excalidraw 要素と同じ **Yjs Doc** に相乗りさせられたので DB を増やさずに済んだ。
ファイルビューアには共有ドキュメントが無いため、ここは専用テーブルを作る
（`supabase/add_file_comments.sql`。**適用にはこの SQL の実行が必要**）。

| 列 | 内容 |
|---|---|
| `id` | uuid。楽観更新のためクライアントで採番する |
| `project_id` / `file_name` | **引き当てキー**（後述） |
| `file_id` | 書かれた時点の版。表示には使わない（調査用） |
| `reply_to` | 返信なら親コメントの id。`null` なら親コメント本体 |
| `x` / `y` | ピンの位置。内容ボックスに対する **0..1 の割合**（後述） |
| `user_id` / `user_name` / `body` | 投稿者と本文 |
| `resolved` / `resolved_at` / `resolved_by_name` | 解決済み |
| `created_at` / `updated_at` | 日時（`updated_at` があれば「編集済み」表示） |

返信を別テーブルに分けず `reply_to` の1テーブルにしたのは、一覧・削除・後始末が1本で済むため。
（ホワイトボードで別マップに分けたのは Y.Map の last-write-wins 対策であって、DB では起きない）

RLS は `project_files` と同じ粒度（認証済みなら読み書き可）。ファイルボックスはページ単位の権限を
持たず「プロジェクトメンバーなら全員が使える」という方針だから（`add_project_files.sql`）。
本人しか編集・削除できない制限はアプリ側で担保する（ホワイトボードのコメントと同じ）。

### 2.2 引き当てキーは `file_id` ではなく `(project_id, file_name)`

ファイルボックスは「同名ファイル＝同じファイルの版」という作りで、画面内エディタでの保存や
WebDAV 保存のたびに `project_files` の行が増える（一覧は最新版だけを見せる）。
`file_id` で縛ると **保存した瞬間にコメントが全部消えたように見える**。
そのため引き当ては版をまたげる `(project_id, file_name)` で行い、`file_id` は記録だけに使う。

FK を張らないのも同じ理由（古い版の行が消えてもコメントを失わないため）。
ファイルそのものを削除した時の後始末は `api/project-files/[action].ts` の `delete` が
同じ条件でまとめて行う（孤児を残さない）。

### 2.3 座標は「割合」で持つ

ホワイトボードは無限キャンバスの scene 座標をそのまま持てたが、ファイルの表示倍率は
ウィンドウ幅で決まる（画像は `maxWidth:100%` で縮む・docx は折り返す）ので px では持てない。
**内容ボックス（`scrollWidth` × `scrollHeight`）に対する 0..1 の割合**で持てば、
別の PC でも別のウィンドウ幅でもだいたい同じ場所を指す。

### 2.4 ピンの描画とスクロール追従

ホワイトボードと同じ方針：

- React は「どのピンが在るか」だけを描く（割合は `data-x` / `data-y` に持たせる）
- rAF ループが `transform` だけを書き換える（スクロールのたびに再レンダーを起こさない）

スクロール量は、ビューアの中で実際にスクロールしている箱（各ビューアが一番外側に持つ
`overflow:auto` の div）を自動で探して `scrollLeft/Top` を差し引く。中身は非同期に描かれるので
見つかるまで定期的に探し直す。

**PDF だけは例外**：ブラウザ内蔵ビューア（iframe）が描いていてスクロール位置を JS から読めない。
そのため PDF のピンは「書類に対する位置」ではなく **「表示領域に対する位置」** になる
（スクロールしてもピンは画面上の同じ場所に留まる）。
書類と一緒に動かすには PDF を自前描画（pdfjs-dist の追加）に切り替える必要があるため、今回は見送り。

### 2.5 コメントモード中のクリックの受け方

コメントモード中だけ、書類全体を透明な面で覆ってクリックを受ける。
PDF は iframe（＝中のクリックが親ドキュメントに届かない）なので、覆うのが唯一の方法。
その代わりホイールは自前でスクロール箱へ流し、覆っている間も書類を送れるようにしてある。

「c」キーは window のキャプチャ段階で拾う。ただし **PDF をクリックした直後はフォーカスが
iframe の中にあり、キーイベントが届かない**（この時はヘッダーのボタンで入る）。

### 2.6 リアルタイム共有

Postgres の変更通知（realtime の有効化）は使わず、書いた側が broadcast を1発投げて相手に
読み直させる（`whiteboardService` の退去通知と同じ作り）。コメントは秒単位の即時性を
要求されない一方、テーブルごとの realtime 設定という追加の DB 設定を増やしたくないため。

書き込みはすべて **先に画面を更新してから DB に流す**（楽観更新）。読み直しに loading state を
持たないのも同じ理由で、相手の書き込みが届くたびに画面がスピナーに差し替わるのを防ぐ。

### 2.7 通知とディープリンク

チケット / ホワイトボードのコメントと同じ経路に相乗りする（追加のマイグレーションは無し）。

- `notifications` テーブルへ insert → ベルのお知らせ＋プッシュ通知
- `/api/slack-notify` へ POST → Slack 通知

飛び先はチケットではないので `mention_context` に `file:{fileId}:{commentId}` の形で入れ、
`Topbar` が解釈して `/{slug}/files?file=..&comment=..` へ飛ばす。
共有リンクも既存のファイル共有リンク（`?file=`）にパラメータを足しただけの形にして、
着地処理を2系統に分けない。

## 3. ファイル構成

| ファイル | 役割 |
|---|---|
| `supabase/add_file_comments.sql` | **要実行**。`project_file_comments` テーブルと RLS |
| `src/app/lib/fileComments.ts` | データ層（読み書き・broadcast 購読） |
| `src/app/lib/fileCommentLink.ts` | 共有リンク・`mention_context` の生成/解析 |
| `src/app/lib/fileCommentNotify.ts` | メンション通知・返信通知 |
| `src/app/components/files/FileCommentLayer.tsx` | ピン層・吹き出し・下書き・一覧 |
| `src/app/components/comments/CommentKit.tsx` | **共通部品**（アバター・⋯メニュー・入力欄・ピンカーソル） |
| `src/app/components/files/FileViewerModal.tsx` | ヘッダーのボタン、ピン層の設置 |
| `src/app/pages/FileBoxPage.tsx` | `?comment=` / `?reply=` の着地 |
| `src/app/components/layout/Topbar.tsx` | お知らせからの飛び先 |
| `api/project-files/[action].ts` | ファイル削除時のコメントの後始末 |

`CommentKit.tsx` はホワイトボードの `CommentLayer.tsx` から切り出したもの。
「全く一緒」を保つために見た目と入力の作法（Enter は改行 / Ctrl+Enter で保存 / @候補の出し方）を
1か所にまとめた。逆に、両者で違ってよいもの（ピンの置き方・座標系・保存先）は入れていない。
コメント一覧ポップアップ（`CommentListPanel`）と本文のメンション着色（`MentionText`）は
ホワイトボード側のものをそのまま共用している。

## 4. 対象外

- 編集モード（画面内 Excel/Word エディタ）中のコメント … エディタが画面を作り替えるので
  ピンの位置が合わず、キー操作もセル入力とぶつかる。閲覧モード限定にしてある
- ブラウザ表示に対応していない形式（.doc / .xls / .pptx など）
- Excel のシートごとのコメント … ピンはブック全体で共有される（シートを切り替えても同じピンが出る）
- PDF のスクロール追従（2.4 参照）
