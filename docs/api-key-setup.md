# API連携の設定手順（Supabase / Vercel）

> この機能を動かすために必要な設定は **Supabase で SQL を1回実行するだけ**です。
> Vercel 側の作業はありません（理由は §2）。
> 初めての方でも迷わないよう、画面の操作から順に書いています。

---

## 全体の流れ

```
 1. Supabase で SQL を1回実行する          … 5分（この作業だけ必須）
 2. コードをデプロイする                    … いつもどおり push するだけ
 3. 動作確認（画面からキーを発行してみる）    … 3分
```

---

## 1. Supabase の作業（必須）

### 1-1. SQL Editor を開く

1. ブラウザで **https://supabase.com/dashboard** を開いてログインします
2. Dev Ticket のプロジェクトをクリックします
3. 左サイドバーの **「SQL Editor」**（電卓のようなアイコン）をクリックします
4. 右上の **「+ New query」** をクリックします

真っ白なエディタが開きます。

### 1-2. SQLを貼り付けて実行する

1. エディタに、このリポジトリの **`supabase/add_api_keys.sql` の中身を全部**コピーして貼り付けます
   - VSCode でファイルを開き、`Ctrl + A`（全選択）→ `Ctrl + C`（コピー）
   - Supabase のエディタで `Ctrl + V`（貼り付け）
2. 右下の緑の **「Run」** ボタンをクリックします（または `Ctrl + Enter`）

### 1-3. 成功したかの確認

下の結果欄に **`Success. No rows returned`** と出れば成功です。

このSQLは**何度実行しても安全**です（冪等といいます）。途中で失敗した場合や、成功したか不安な場合は、そのまま**もう一度 Run しても問題ありません**。

<details>
<summary>❌ エラーが出た場合</summary>

| エラーメッセージ | 意味 | 対処 |
|---|---|---|
| `relation "public.projects" does not exist` | プロジェクトを間違えている | 左上のプロジェクト名を確認し、Dev Ticket のものを選び直す |
| `relation "public.profiles" does not exist` | 初期スキーマが入っていない | 先に `supabase/schema.sql` を実行する |
| `permission denied` | 権限のないアカウント | プロジェクトのオーナー権限があるアカウントでログインし直す |

上記以外のエラーが出たら、**エラーメッセージ全文をコピーして共有してください**。
</details>

### 1-4. 何が作られたかの確認（任意）

左サイドバーの **「Table Editor」** を開くと、テーブル一覧に次の2つが増えています。

- **`api_keys`** … 発行したAPIキー（中身は空。画面から発行すると増えます）
- **`ticket_wbs_seq`** … WBSの採番用カウンタ（中身は空。APIから登録すると増えます）

`api_keys` には `key_hash`（照合用のハッシュ）と `key_cipher`（暗号化した平文）の列がありますが、**どちらもそのままではキーとして読めません**。復号に必要な鍵は Vercel の環境変数側にしか無いため、**このDBが丸ごと漏れてもキーは復元できません**。

> ⚠️ **すでにこのSQLを実行したことがある方へ**
> `key_cipher` 列を後から追加しています。**もう一度 Run してください**（何度実行しても安全です）。
> 再実行前に発行したキーは平文を保存していないため、画面のプロンプトへ埋め込めません。
> その場合は「APIキー」タブで**発行し直して**ください（古いキーは失効させておくと安全です）。

## 2. Vercel の作業（**ありません**）

「本当に何もしなくていいの？」と不安になると思うので、理由を説明します。

### 2-1. 環境変数の追加は不要

新しいAPIが使う環境変数は次の2つですが、**どちらも既存の機能がすでに使っているもの**です。

| 環境変数 | 使っている既存機能 |
|---|---|
| `VITE_SUPABASE_URL` | 招待メール、Slack通知、ファイルボックス など |
| `SUPABASE_SERVICE_ROLE_KEY` | 同上 |

つまり Vercel には**もう設定済み**です。追加も変更も要りません。

<details>
<summary>念のため確認したい場合の手順</summary>

1. https://vercel.com/dashboard を開く
2. Dev Ticket のプロジェクトをクリック
3. 上部の **「Settings」** タブ → 左メニューの **「Environment Variables」**
4. 一覧に `VITE_SUPABASE_URL` と `SUPABASE_SERVICE_ROLE_KEY` があればOK

※ 値は伏せ字で表示されます。**値を確認・変更する必要はありません。**
</details>

### 2-2. APIの追加設定も不要

Vercel は `api/` フォルダの中のファイルを**自動的にAPIとして公開します**。今回追加した2ファイルは、デプロイした瞬間に次のURLで使えるようになります。

- `https://（あなたのドメイン）/api/v1/tickets`（外部のAI／CIが叩く）
- `https://（あなたのドメイン）/api/v1/context`（同上）
- `https://（あなたのドメイン）/api/api-keys/create`（管理画面が使う）
- `https://（あなたのドメイン）/api/api-keys/reveal`（同上）

なお、キーの暗号化に使う鍵は既存の `SUPABASE_SERVICE_ROLE_KEY` から自動的に導出されるため、**暗号鍵用の環境変数を追加する必要もありません**。

`vercel.json` の変更も不要です（`/api/` 配下はもともと画面側の転送ルールから除外されています）。

### 2-3. 費用も増えません

- Vercel の関数はすでに21本動いており、1本増えても料金体系上の区分は変わりません
- 呼び出し回数もフェーズごとに数十回程度で、既存機能に比べて誤差です
- Supabase も、作られるチケットの行数は人が手で作るのと同じです
- 新しい外部サービス（Redis など）は一切追加していません

## 3. デプロイ

いつもどおりです。特別な手順はありません。

```
git add -A
git commit -m "API連携（APIキーでのチケット登録）を追加"
git push
```

Vercel が自動でビルド・デプロイします。Vercel の画面で **Deployments** が緑の「Ready」になれば完了です。

> ⚠️ **順序に注意**: 先に §1 の SQL を実行してからデプロイしてください。
> 逆順でも壊れませんが、SQL 未実行のまま画面から発行しようとすると
> 「APIキーのテーブルがまだありません」というエラーが出ます。

> ⚠️ **キーの発行はデプロイ後の環境で行ってください。**
> キーの生成と暗号化はサーバー側で行うため、`npm run dev`（Vite開発サーバー）では
> APIが動かず発行できません（「APIサーバーが応答しませんでした」と表示されます）。
> メニューやモーダルの見た目の確認は `npm run dev` でも可能です。

## 4. 動作確認

### 4-1. キーを発行する

1. Dev Ticket に**管理者アカウント**でログインします
2. 任意のプロジェクトの**スプリント一覧**を開きます
3. スプリントの帯にある **［＋ 新規チケット ▾］** をクリックします
4. メニューの **「🔑 API連携」** をクリックします
5. **「APIキー」** タブ → **「＋ 新規発行」**
6. 用途名に `テスト用` と入力 → **「発行する」**

`dvt_live_` で始まる文字列が表示されれば成功です。

> キーは暗号化して保存されるため、あとから **「APIキー」タブの 📋 アイコン**で
> コピーし直すこともできます（控え忘れても再発行は不要です）。

### 4-2. 実際にチケットを登録してみる

発行画面の **「✨ プロンプトコピー（APIキー込み）」** を押し、Claude Code などのAIに貼り付けて、

> この内容でテスト用のチケットを1件登録して

と頼んでみてください。スプリントにチケットが増えれば成功です。

<details>
<summary>コマンドで確認したい場合（PowerShell）</summary>

```powershell
$key = "dvt_live_ここに発行したキー"
$headers = @{ Authorization = "Bearer $key" }

# ① 使えるスプリントやメンバーを確認する
Invoke-RestMethod -Uri "https://（あなたのドメイン）/api/v1/context" -Headers $headers | ConvertTo-Json -Depth 5

# ② チケットを1件登録する（sprintId は ① の結果から選ぶ）
$body = @{
  sprintId = "（①で確認したスプリントID）"
  tickets  = @(@{ title = "APIからのテスト登録"; priority = "低" })
} | ConvertTo-Json -Depth 5

Invoke-RestMethod -Uri "https://（あなたのドメイン）/api/v1/tickets" `
  -Method Post -Headers $headers -ContentType "application/json" -Body $body
```
</details>

### 4-3. 後片付け

テスト用のキーは **「APIキー」タブ → 🚫 アイコン** で失効させておいてください。

## 5. 困ったときは

| 症状 | 原因 | 対処 |
|---|---|---|
| メニューに「API連携」が出ない | 権限 | 管理者（admin / owner）でログインしているか確認 |
| 「API連携」がグレーで押せない | 権限またはプラン | 管理者以外は使えません。プランで一括作成がOFFの場合も使えません |
| 発行時に「テーブルがまだありません」 | SQL未実行 | §1 をやり直す |
| 発行時に「権限がありません（管理者のみ）」 | 権限 | 管理者アカウントか確認する |
| 発行時に「APIサーバーが応答しませんでした」 | ローカルで実行している | `npm run dev` ではキーを発行できません。デプロイした環境で操作する |
| 「テーブルが古い形式です」 | `key_cipher` 列がない | §1 の SQL をもう一度 Run する |
| 使い方タブに「以前の方式で発行されている」と出る | 暗号化対応より前に発行したキー | 「APIキー」タブで発行し直す（古いキーは失効させる） |
| APIが `401` を返す | キーが無効／失効／期限切れ | 画面の「APIキー」タブで状態を確認。必要なら再発行 |
| APIが `403` を返す | プランの上限 | スプリントのチケット数上限に達しています |
| APIが `429` を返す | リクエストが多すぎる | 1キーにつき1分あたり60回まで。少し待つ |
| APIが `404`（スプリントが見つからない） | キーのプロジェクト違い | そのキーは別プロジェクト用です。対象プロジェクトで発行し直す |
| 「WBSの採番に失敗しました」 | SQL未実行 | §1 をやり直す（`reserve_ticket_wbs` が作られていません） |

## 6. 運用上の注意

- **キーはパスワードと同じです。** Git にコミットしないでください
- 漏れた可能性があれば、**その場で失効させて発行し直して**ください。失効は即座に効きます
- 「APIキー」タブの **「最終利用」** を見ると、そのキーがまだ使われているか分かります。使われていないキーは失効させておくと安全です
- 有効期限は既定で90日です。無期限も選べますが、漏れたときに影響が続くため推奨しません
